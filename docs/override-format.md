# 覆盖文件的字节格式

`/Library/Displays/Contents/Resources/Overrides/DisplayVendorID-<v>/DisplayProductID-<p>` 是一个 plist，`scale-resolutions` 数组里的每一项都是**大端**的四字节字。

## 三种条目长度

| 长度 | 结构 | 含义 | 实例（Apple 自带文件） |
| --- | --- | --- | --- |
| 8 字节 | `w h` | 仅声明像素尺寸 | `0000190000000e10` = 6400×3600 |
| 12 字节 | `w h flags` | 普通（1x）模式，`flags` 多为 `0x00000001` | `000006900000041a00000001` = 1680×1050 @1x |
| 16 字节 | `w h 0x00000001 0x00200000` | **HiDPI 模式**：渲染 `w×h` 像素，逻辑尺寸为 `w/2 × h/2` | `00000a00000006400000000100200000` = 2560×1600 像素 → 1280×800 HiDPI |

第 4 个字 `0x00200000` 是 HiDPI 标记。去掉它，系统只当成一个奇怪的 1x 模式。

## 证据不是猜的

这些数字不是从博客抄的，是直接读 Apple 在这台机器上的文件反推的：

```
$ plutil -p /System/Library/Displays/Contents/Resources/Overrides/DisplayVendorID-610/DisplayProductID-a040
  "scale-resolutions" => [
    0 => {length = 9,  bytes = 0x00000f000000096000}
    ...
    5 => {length = 16, bytes = 0x00000a00000006400000000100200000}
    8 => {length = 16, bytes = 0x00000780000004380000000100200000}
    ...
    18 => {length = 16, bytes = 0x00000f00000009600000000900a00000}
  ]
```

`0x0000078000000438` = 1920×1080，配合 `0x00200000` 就是"1920×1080 像素 → 960×540 逻辑"的 HiDPI 档位。同一文件第 18 项尾巴是 `0x00000009 0x00a00000`，属于另一类（高刷/色彩相关）标记，本工具不生成。

全系统 245 个带 `scale-resolutions` 的 override 文件里，16 字节条目共 611 个、12 字节 1856 个、8 字节 291 个、9 字节 63 个 —— 上述结构覆盖了绝大多数。

## 本工具生成的选择

只生成 16 字节 HiDPI 条目，不碰其它长度。原因：

- 8/9 字节条目语义未在公开材料中定义清楚，生成它们属于猜；
- 12 字节的 1x 模式本来就有，加进去只会让显示面板变长；
- 16 字节格式同时被 Apple 自带文件与社区脚本验证过。

`logical → entry` 的换算只有一行：`(logicalW*2, logicalH*2, 0x1, 0x00200000)`。

## 一个反直觉的细节

大尺寸面板的 HiDPI 档位不一定是面板分辨率的 1/2。比如 2880×1800 的内置屏，系统还列了 `1680×1050 HiDPI`，其像素是 3360×2100 —— 比面板还大，靠 GPU 超采样缩放。

所以**不能**用"像素面积最大的模式"反推面板尺寸。本工具取"最大的 1x 模式"作为面板像素（`Sources/YueHiDPICore/Modes.swift`），否则 2880×1800 的屏会被误判成 3360×2100，档位推算跟着错。

## Vendor / Product 的十六进制写法

目录名与文件名都是**小写、无 `0x` 前缀、不补零**：`DisplayVendorID-610`（1552）、`DisplayProductID-a03e`（41022）。写成 `0x610` 或 `0610` 系统不认。
